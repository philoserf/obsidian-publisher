# A Theory of Obsidian Publisher

## What this system is for

Obsidian Publisher exists to solve a specific problem in a specific workflow: a person writes notes in Obsidian, marks some of them as ready for publication, and wants those notes to appear in a Hugo-powered website hosted on GitHub—without leaving Obsidian, and without requiring a desktop operating system. The last constraint is the one that shapes everything else. The author uses Obsidian on iOS. There is no local git, no shell, no filesystem access beyond the vault. Every interaction with GitHub must happen over HTTPS, through the REST API, using Octokit.

The core entities in the problem domain are: a **vault** (Obsidian's opaque file store, the source of truth for content), a **note** (a markdown file with YAML frontmatter, potentially referencing images and other notes), a **publishing target** (a GitHub repository structured for Hugo), and a **publish event** (the act of transforming notes from Obsidian's dialect into Hugo's dialect and delivering them to the target). There is also a **publish gate**: only notes whose frontmatter contains `status: publish` are eligible. Everything else in the vault is invisible to the system.

The system does not model a blog, a site, or a content management system. It models a bridge. On one side, Obsidian's markdown with wikilinks, image embeds, callouts, and comments. On the other, Hugo's markdown with ref shortcodes, standard image paths, notice shortcodes, and mermaid shortcodes. The bridge is unidirectional—Obsidian to GitHub, never back—and stateless: each publish event is independent, with no memory of what was published before. There is no diff, no sync, no conflict resolution. You push; whatever's there gets overwritten.

## The organizing ideas

**Four components, one seam.** The system is split into four classes that form a strict call chain: `main.ts` (plugin lifecycle and command dispatch) → `Publisher` (orchestration and vault scanning) → `ContentProcessor` (syntax transformation) and `GitHubService` (API interaction). Publisher is the only component that talks to both ContentProcessor and GitHubService; the two never see each other. This is the essential separation: content transformation knows nothing about delivery, and delivery knows nothing about content. A maintainer could replace Hugo with a different static site generator by rewriting ContentProcessor alone, or switch from GitHub to GitLab by rewriting GitHubService alone, without touching the other.

The seam between these two concerns lives inside `Publisher.publishFileToTarget()`, where processed content and resolved images are assembled into a flat list of `{ path, content }` entries and handed to `GitHubService.commitFiles()`. This is the narrowest point in the system—the interface between "what to publish" and "how to deliver it"—and it's deliberately thin. The entries are just paths and bytes. GitHubService doesn't know they're markdown and images; ContentProcessor doesn't know they'll become git blobs.

**Two publishing workflows, one code path.** The system supports direct commits to a branch (legacy) and a branch-plus-PR workflow (current default). These share `publishFileToTarget()` and `prepareBatch()` for the actual work; the workflows differ only in whether they create a branch before and a PR after. The branching decision is made in `main.ts`, not in Publisher—main inspects `usePullRequests` and calls different methods. This means Publisher exposes four public methods (`publishNote`, `publishAll`, `publishNoteWithPR`, `publishAllWithPR`) that are really two methods times two modes. The duplication is real but bounded: the branch-creation and PR-creation logic wraps the shared core rather than interleaving with it.

**Atomicity through the Git Trees API.** `commitFiles()` is the most mechanically complex method and the one most likely to confuse a reader who doesn't understand the GitHub Git Data API. It builds a commit by hand: get the current branch SHA, fetch the commit's tree, create a blob for each file, create a new tree referencing all the blobs plus the existing base tree, create a commit pointing to that tree, and update the branch ref. This is not an artifact of over-engineering; it's the only way to commit multiple files atomically through the REST API without using the Contents API (which is file-by-file and would create one commit per file). The base_tree parameter in createTree is what preserves files that aren't being published—without it, every commit would delete everything else in the repository.

**One parser, one schema module.** Frontmatter handling lives in a single module, `schema.ts`, which exports `splitFrontmatter()` (regex match + `parseYaml`), `hasPublishFlag()` (parsed gate check), and `validateFrontmatter()` (required-field check). Publisher and ContentProcessor both delegate to it. The gate is a parsed check — `status: "publish"` (quoted) resolves correctly — and the required-field list (`title`, `date`) is validated as a preflight step before any GitHub API activity, so a note missing required fields fails fast with a clear error rather than producing a mis-rendered post. An earlier version used a regex for the gate in Publisher and a separate `parseYaml` call in ContentProcessor; those two paths disagreed on quoted scalars. Consolidating them removed that class of silent failure.

**Content transformation is ordered and partitioned.** The `process()` method applies eight transformations in a fixed sequence: strip comments, convert highlights, convert callouts, convert mermaid, convert image references, convert note embeds, convert wikilinks. The order matters in two ways. First, images are _extracted_ (their names collected) before image references are _converted_ (the syntax rewritten). This ensures the image list reflects the original Obsidian syntax, not the Hugo output. Second, `convertImageReferences()` and `convertNoteEmbeds()` both match the same regex (`![[...]]`) but partition the match space using `IMAGE_EXTENSIONS`: images get rewritten to standard markdown image syntax, non-images get rewritten to Hugo ref links. Each function returns the original match unchanged for the cases it doesn't own. This partition is the invariant that prevents double-conversion, and breaking it (say, by adding a new embed type that's neither image nor note) would require rethinking the dispatch.

**Settings are immutable per publish.** When settings change, `saveSettings()` reconstructs the entire Publisher (and with it, ContentProcessor and GitHubService). There is no mechanism to update settings mid-publish. This simplifies reasoning about consistency—a single publish event always uses a single, frozen configuration—but it means every keystroke in the settings UI triggers a full reconstruction. (Issue #114 notes this should be debounced.)

## The seams

**Obsidian's vault API** is the primary external boundary. The system reads files through `vault.read()` (markdown content as strings) and `vault.readBinary()` (images as ArrayBuffers). It discovers files through `vault.getMarkdownFiles()` and `vault.getFiles()`. It never writes to the vault. The vault API is thin and stable, but it introduces one significant constraint: file lookup by name. `resolveImages()` builds a `Map<filename, TFile>` from `vault.getFiles()`, keyed by `file.name` (the basename, not the full path). If two images in different vault folders share a name, the Map overwrites and the wrong image may be uploaded. This is a known issue documented in `.issues/` and is probably the most consequential bug in the system. It doesn't manifest in vaults where image names are unique, which may explain why it hasn't been fixed yet.

**GitHub's REST API** is the other external boundary, accessed exclusively through Octokit. The system uses a narrow slice of the API: `repos.get` (connection test), `git.getRef` / `createRef` / `deleteRef` / `getCommit` / `createBlob` / `createTree` / `createCommit` / `updateRef` (the commit pipeline), `pulls.create` (PR creation), and `issues.addLabels` (PR labeling). Rate limiting is handled implicitly—blobs are created sequentially in a loop, not in parallel—but there's no explicit rate-limit detection or backoff. For a single note with a few images, this is fine. For a batch publish of dozens of notes with many images, each blob creation is a separate API call, and the sequential loop is the only throttle.

**Hugo's expectations** form a softer, less explicit boundary. The system assumes Hugo's content structure (`content/posts/` for markdown, `static/images/` for assets), its URL conventions (sanitized filenames as slugs), its frontmatter requirements (a `date` field must exist), and its shortcode syntax (`{{< ref >}}`, `{{< notice >}}`, `{{< mermaid >}}`). The notice shortcodes and mermaid shortcodes are specific to the hugo-coder theme, not Hugo itself—a fact that isn't surfaced anywhere in the code or settings. A user who changed Hugo themes would find their callouts and mermaid diagrams broken. The coupling to hugo-coder is real but implicit.

**The callout type map** (`CALLOUT_TYPE_MAP`) is where Obsidian's vocabulary meets Hugo's. Obsidian defines about 20 callout types; hugo-coder's notice shortcode accepts 7. The map collapses them: `warning`, `caution`, and `attention` all become `warning`; `failure`, `danger`, `error`, and `bug` all become `error`. Unknown types fall back to `note`. This is a lossy translation, and the loss is intentional—hugo-coder doesn't have a concept of `danger` vs `failure`, so the closest available type is chosen. A maintainer adding support for a different theme would need to replace this map, and possibly the entire shortcode output format.

**The test boundary** is worth calling out explicitly. Tests mock three external modules: `obsidian` (the vault and YAML parser), `@octokit/rest` (GitHub API client), and `@octokit/request-error` (typed HTTP errors). The mocks are loaded via `test-preload.ts` in bunfig.toml, so they apply globally. The `parseYaml` mock is notably simpler than the real Obsidian parser—it handles flat key-value pairs and simple arrays but not nested structures, multi-line strings, or YAML edge cases. Tests that exercise frontmatter processing are testing against this simplified parser, which means YAML-related bugs in production may not surface in tests. This is documented as issue #129.

## What the system accommodates easily, and what it doesn't

**Easy changes:** Adding a new content transformation (say, converting Obsidian's `> [!quote]` to a different shortcode, or handling a new embed syntax) follows a clear pattern: add a private method to ContentProcessor, slot it into the `process()` pipeline at the right position, and add tests. The transformation pipeline is purely sequential string manipulation with no shared state between steps. Similarly, adding a new setting is mechanical: add the field to `PublisherSettings` and `DEFAULT_SETTINGS`, add the UI element in `settings.ts:display()`, and use it wherever needed. The settings type is the single source of truth.

**Moderate changes:** Supporting a different static site generator (not Hugo) would require replacing ContentProcessor's output format—different shortcode syntax, different frontmatter conventions, different URL patterns. The separation between ContentProcessor and GitHubService means this wouldn't touch the delivery layer. But the Hugo assumptions run deep in ContentProcessor (the `ref` shortcode, the `notice` shortcode, the `static/` prefix stripping, the date-field enforcement), so this would be a near-total rewrite of that class, not a configuration change.

**Hard changes:** Three things would require rethinking fundamentals. First, **bidirectional sync** (pulling changes from GitHub back to Obsidian) would violate the system's core assumption of unidirectional, stateless publishing. There's no tracking of what's been published, no content hashing, no conflict model. Second, **incremental publishing** (only uploading changed files) would require either local state tracking or diffing against the GitHub repository's current contents. The system currently has no concept of "what's already there"—it pushes files and trusts that the overwrite is correct. Third, **publishing to non-GitHub targets** would require abstracting GitHubService behind an interface, which would also require abstracting away the Git Trees commit model (since not all hosting platforms expose low-level git primitives through their APIs). The commit pipeline in `commitFiles()` is deeply specific to GitHub's Git Data API.

**Where a confused maintainer would cause damage:** The content transformation ordering in `process()` is fragile in a way that's not obvious. Moving `convertImageReferences()` after `convertWikilinks()` would break image embeds, because wikilinks and image embeds share similar syntax. The image/note-embed partition depends on `IMAGE_EXTENSIONS` being checked before the regex match is consumed. A maintainer who added a new transformation that consumed `![[...]]` matches without checking the extension would silently eat content intended for another handler. The correct place to look when adding new embed handling is the three functions that all match `![[...]]`: `extractImages`, `convertImageReferences`, and `convertNoteEmbeds`. They must be understood as a unit.

Similarly, `markResultsFailed()` in Publisher is easy to overlook but load-bearing. If `commitFiles()` throws after `prepareBatch()` has already marked individual results as successful, `markResultsFailed` walks back those successes. Without it, batch publishing would report files as successfully published when the commit actually failed. A maintainer who changed the batch error-handling flow without understanding this would produce false-positive success reports.

## Uncertainties

I'm inferring the hugo-coder dependency from the shortcode names (`notice`, `mermaid`) rather than from any explicit documentation or configuration. It's possible the author uses custom shortcodes that happen to share these names, or that the shortcodes are defined in the target Hugo repository rather than in a theme. The code gives no way to tell.

The `imageUrlPath()` method strips a `static/` prefix from `imageDir` to produce the URL path, with a comment explaining that Hugo serves `static/` at the root. This is correct for standard Hugo configurations, but I can't tell whether the author's Hugo setup is standard. If `imageDir` doesn't start with `static/`, the prefix strip is a no-op and the path passes through unchanged—a reasonable fallback, but one that suggests the method was written for a specific directory layout.

The settings migration logic (line 54 of main.ts) checks for `data.usePullRequests === undefined` to detect existing users upgrading from pre-PR versions. This works exactly once: after the first save, the field is defined. But the check uses `data` (the raw loaded data) rather than `this.settings` (the merged defaults), which is correct—`Object.assign` would have already set it to `true` from defaults. I mention this because the subtlety is easy to miss, and a refactor that changed the load order could silently break the migration.

The `.issues/` directory documents seven known problems, several of which are genuinely significant (the basename collision in image lookup, the regex-vs-parser inconsistency in publish gating, the RequestError wrapping that discards HTTP status codes). These are the places where the system's theory is thinnest—where the code works for the author's vault and workflow but would fail for different inputs. Whether they represent intentional trade-offs or incomplete work, I can't say from the code alone. The fact that they're documented suggests awareness; the fact that they're open suggests either low priority or low confidence in the right fix.

Finally: the system has no integration tests. All tests mock the external boundaries (vault, GitHub, YAML parser). There is no test that exercises the actual Obsidian or Octokit APIs, which means the contract between the code and its dependencies is verified only by the mocks' fidelity. The mock YAML parser is known to be unfaithful. This is a common and defensible choice for a plugin—you can't easily spin up Obsidian in CI—but it means the test suite validates internal consistency, not external correctness. A maintainer should understand that passing tests prove the transformations work as designed, not that they work as deployed.
