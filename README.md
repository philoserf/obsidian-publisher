# Obsidian Publisher\n\n![Status: Stable](https://img.shields.io/badge/Status-Stable-brightgreen.svg)\n\nPublish [Obsidian](https://obsidian.md/) notes to GitHub for [Hugo](https://gohugo.io/) processing. Tailored for [philoserf.com](https://philoserf.com).\n\n## You probably shouldn't install this\n\nThis is personal tooling, not a general-purpose plugin. It is opinionated in ways that only make sense for one person's workflow:\n\n- **Single user.** The only known installation is the maintainer's. Breaking changes ship without migration paths (see `CHANGELOG.md` — 1.4.0 renamed the publish sentinel, 1.5.0 retired `removePublishFlag` and the `{{< ref >}}` wikilinks, 1.6.0 retired the direct-commit publish mode entirely).\n- **One target shape.** The Hugo destination is expected to use `content/posts/`, `static/images/`, and the shipped `hugo-shortcodes/` (callout + mermaid) installed in the site's theme. Other layouts will see broken links or missing renderers.\n- **PR workflow only, mandatory.** Every publish creates a timestamped feature branch and opens a PR against `baseBranch`. There is no direct-commit escape hatch. A second publish is refused while one is still running — on a slow connection, re-tapping a button that has not visibly responded would otherwise open a duplicate branch and PR, and the plugin cannot delete a branch or PR it opened.\n- **Required frontmatter.** Notes must carry `status: publish`, plus a non-empty `title` and `date`. Missing or empty required fields fail the publish per-note.\n- **No issue triage for feature requests.** Bugs are welcome; feature requests from other users will almost always be closed as out-of-scope.\n\nIf you want something similar, the code is MIT-licensed — fork it and adapt. Don't expect upstream to accommodate your workflow.\n\n## From the command line\n\n`obsidian publisher:preflight path="Drafts/Note.md"` runs every check a publish makes before it reaches GitHub — frontmatter parse, `status: publish`, required fields, the transform and image resolution — and prints `ok` or the reason the note would fail. Any warnings (a missing image, say) follow, one per line; the first line is always the verdict. It needs no GitHub token and opens no branch, so it works on a device that has never entered one.\n\n`obsidian publisher:publish path="Published/Note.md"` does what the publish-current-note command does for the named note. The Obsidian CLI stops waiting for a plugin after a few milliseconds, far less than a publish takes, so it answers at once: `started <id>`, or, when it cannot start, the reason — `File not found: …`, `Cannot publish: …` (the token is missing on this device, say), or `A publish is already running`. `obsidian publisher:result id=<id>` then prints `running <id>` until the publish is done, and after that its result in preflight's shape: `ok` and the pull request URL, or the reason it failed, then any warnings. Results are kept in memory for the last 50 runs, until the plugin reloads.\n\n## Content Transformations\n\nThe plugin converts Obsidian-specific syntax to Hugo-compatible markdown during publish:\n\n| Obsidian | Hugo |\n| -------------------------- | ---------------------------------------------------- |\n| `[[Page Name]]` | `[Page Name](/posts/page-name/)` (if in publish set) |\n| `[[Page Name#Heading]]` | `[Page Name#Heading](/posts/page-name/#heading)` |\n| `[[Page\|Display]]` | `[Display](/posts/page-name/)` |\n| `[[#Heading]]` | `[Heading](#heading)` (same page, always resolves) |\n| `![[image.png]]` | `![image.png](/images/image.png)` |\n| `![[image.png\|alt]]` | `![alt](/images/image.png)` |\n| `![[image.png\|300]]` | `![image.png](/images/image.png)` (sizing stripped) |\n| `![[image.png\|alt\|300]]` | `![alt](/images/image.png)` |\n| `![[Note Name]]` (embed) | `[Note Name](/posts/note-name/)` (if in publish set) |\n| `![[Note#Heading]]` | `[Note#Heading](/posts/note/#heading)` |\n| `[[folder/Page Name]]` | `[folder/Page Name](/posts/page-name/)` |\n| `![[folder/image.png]]` | `![image.png](/images/image.png)` |\n| `%%comment%%` | Removed, including when it wraps code |\n| `==highlight==` | `<mark>highlight</mark>` |\n| `> [!note] Title` | `{{< callout note "Title" >}} … {{< /callout >}}` |\n| ` ```mermaid ` | `{{< mermaid >}} … {{< /mermaid >}}` (any fence) |\n\nWikilinks and note embeds only resolve to URLs for notes in the **current publish set** (the notes being published in this operation). Out-of-set references degrade to plain text — so you can't publish a link to a note that isn't also being published. The one exception is a same-page anchor (`[[#Heading]]`): its target is the document itself, so it always resolves.\n\n**Blocks nest.** A callout holds whatever you put in it — paragraphs separated by a bare `>`, fenced code samples, comments — and the whole block converts, not just the lines above the first fence. A `%%` comment is removed whether or not it wraps a code span or a fenced block, and an image referenced only inside one is never uploaded. Mermaid is recognized in any fence the parser accepts: tildes, four or more markers, and an info string beyond the bare language.\n\n**Paths are addressing, not names.** Obsidian writes a reference path-qualified when the bare filename would be ambiguous, and unconditionally when Files & Links -> **New link format** is set to "Absolute path in vault" or "Relative path to file". The directory tells the plugin which file you mean; the slug, the committed filename and the URL all come from the filename alone. A link that does not resolve still degrades to the full text you wrote.\n\n**Code is left alone.** Everything inside a fenced code block or an inline code span is exempt from every transformation in the table — a `==x==` or `[[Page]]` in a code sample publishes verbatim rather than being rewritten. Mermaid is the deliberate exception: it is the one transformation that acts _on_ a fenced block.\n\n**Aliases become redirects.** A note's `aliases` frontmatter is rewritten into the URLs those titles produced (`DNA as Remix Culture` → `/posts/dna-as-remix-culture/`), so Hugo emits a working redirect stub instead of one at a path the site never served. Values that already start with `/` pass through untouched, which is how you pin an exact old URL.\n\n### Settings worth knowing\n\n- **Stripped frontmatter fields.** Removed from published notes; defaults to `status`, `lastmod`, `cssclass`, `cssclasses`, `position`, `created`, `modified`. `aliases` is deliberately _not_ in that list — stripping it would suppress the redirects above.\n- **Frontmatter template.** Fields injected into every published note, without overriding what the note already sets. Input that is not `key: value` lines is rejected in the settings field, and nothing is stored, rather than half-parsed — a partial recovery was the one way a value you never wrote could reach a commit.\n- **Shortcode names.** `callout` and `mermaid` by default; change them to match your theme.\n- **`contentDir` / `imageDir`.** Destination paths in the site repo; the URL prefix in the table above is derived from `contentDir`. A path with a `.` or `..` segment, or a `~` anywhere in it, is rejected whole rather than repaired — the publish then fails with "… is required" instead of quietly writing somewhere else. Surrounding whitespace and edge slashes are still normalized away; what is never done is stripping the _dangerous_ parts, because removing them can construct the thing being removed (`.~./posts` used to become `../posts`).\n\nCallout types pass through from Obsidian verbatim (no collapse to a fixed set). The destination Hugo site must define `callout` and `mermaid` shortcodes in `layouts/shortcodes/`. Reference implementations ship in `hugo-shortcodes/` — copy them into your theme. The shortcode names are configurable in the plugin settings (default `callout` and `mermaid`).\n\nHeading anchors (`[[Page#Heading]]`) assume the destination Hugo site uses the default `autoIDType: "github"`, which preserves Unicode letters. Sites configured with the opt-in `autoIDType: "github-ascii"` will see mismatched `#fragment` links — pages load, but in-page jumps to non-ASCII headings won't resolve.\n\nPage slugs, committed filenames, and heading anchors all share one rule: NFC-normalize, lowercase, keep Unicode letters and digits, and turn whitespace into hyphens. So a note titled `Rōnin…` publishes at `/posts/rōnin-…/`, matching what Hugo generates by default. Sites that set `removePathAccents: true` will see mismatched links, for the same reason as `github-ascii` above.\n\nBecause the destination filename follows that same rule, **renaming a note renames its published file**. Publishing the one note leaves the previous file in the site repo; the next Publish All removes it (see below). Add the old URL to the note's `aliases` before republishing if you want it to keep resolving.\n\n## Publish All keeps the posts directory in step\n\nPublish All treats `contentDir` as exactly the publish set. It reads the directory on `baseBranch` once, and every `.md` file directly in it that no `status: publish` note produces — a retired, merged, renamed or recalled note — is deleted in the same commit. Nothing else is touched: subdirectories, `.gitkeep`, Hugo's `_index.md`, images in `imageDir`, and anything outside `contentDir` stay as they are. Redirects for removed posts are the site's business, not the plugin's.\n\nBecause a deletion is only right when the publish set is whole, the run is all or nothing, with these guards:\n\n- A note that fails to read, parse or validate stops the run before any branch exists, so a frontmatter typo cannot delete its own post.\n- An empty publish set publishes and deletes nothing.\n- When there is something to delete, a dialog lists every post first; anything but the confirm button cancels, with nothing committed.\n- The pull request lists every deletion, and is the last gate before merge.\n\nPublishing a single note never deletes anything: it cannot know the whole set.\n\n## Security\n\nThis plugin requires a GitHub Personal Access Token (PAT) to publish content.\n\n- **Use a fine-grained token** scoped to your target repository with `contents:write` and `pull_requests:write` permissions. Avoid classic tokens with broad `repo` scope.\n- **Token storage:** The token is kept in Obsidian's keychain (Settings → Keychain), which encrypts it with the operating system's secure storage; the plugin's `data.json` holds only the secret's name. Obsidian does not sync keychain secrets, so choose or enter the token once on each device you publish from. Requires Obsidian 1.13.0.\n- **Upgrading:** A plaintext token in `data.json` from before the keychain is ignored and dropped on the next save; it is no longer moved into the keychain (#382). Enter the token in Settings → Keychain on each device.\n- **Recommendations:** Use a token scoped to a single repository.\n\n## Alternatives\n\n- [Enveloppe](https://github.com/Enveloppe/obsidian-enveloppe) — publish Obsidian notes to GitHub with broader CMS support (Jekyll, Hugo, etc.).\n- [Digital Garden](https://github.com/oleeskild/obsidian-digital-garden) — publish notes to a static site with its own theme and hosting.\n
